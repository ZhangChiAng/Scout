# 知乎话题、同题回答与偏好学习

知乎使用单一 owner、所有话题共用的字面关键词偏好，独立于橘鸦日报的反馈和模型档案。
采集器负责真实知乎会话、搜索、问题回答列表和正文；Scout 只通过本机 HTTP 协调任务、保存
SQLite 状态和发送飞书卡片。Cookie 留在采集器，日志和报告不包含凭据。

## 飞书操作

先升级独立采集器，使 `/v1/health` 的 capabilities 包含 `question_answers`，再重启
`scout-feedback.service`。未具备此能力时，新扫描会明确拒绝启动；已保存的旧任务按原快照恢复。
发送管理卡片：

```bash
uv run --locked python -m scout.zhihu manage
```

在卡片新增话题，填写名称、搜索词（中英文逗号或换行分隔），选择近 7 天、近 30 天或不限。
搜索词忽略大小写，保存与执行时统一 casefold 并合并重复词；`GPT-6` 和 `gpt-6` 只查询一次，
`gpt6` 与 `gpt-6` 保留为两个不同写法。
默认近 30 天；可修改、停用和重新启用。立即扫描可选单个话题或全部启用的话题；全部扫描会为
每个话题创建独立扫描 ID，每个扫描最多接纳 200 个搜索种子。

每日扫描默认关闭。启用时必须填写北京时间 `HH:MM`，从接下来的该时刻开始执行（当天时刻已过则从次日开始），常驻 listener 到时创建当天任务；
重启后可补上当天已到时但尚未创建的任务，每个话题每天最多一次。停用话题阻止后续新任务，
已经创建的任务继续使用保存的配置。开启自动扫描前不设定默认时刻。

内容卡展示标题、正文摘录、发布日期和链接。“喜欢”直接保存；“不喜欢”需填写正文中实际出现的
降权词，用中英文逗号分隔。忽略大小写，去除首尾空白和重复词，任何词未字面命中正文时整次提交
不保存。通过“修改反馈”替换当前标签，旧修订留存。在管理卡查看过滤结果，选择有完整正文的
条目发送补标卡，纠正误筛；仅实际提交的标签参与学习。

管理卡显示样本数量、学习状态、近期扫描请求和扫描状态。回调只校验身份和表单、保存 SQLite
操作。采集、训练和发送均由后台推进。复用已有 `scout_owner`，没有创建用户列表或多用户偏好。

## 候选与排序

每个搜索词分别搜索最新和综合结果，每个查询最多 3 页。仅接纳回答和专栏文章，200 个上限只
限制去重后的直接命中种子；其他查询仍记录实际覆盖和因种子上限未接纳的数量。

回答优先使用搜索记录的 question_id，缺失时请求该回答详情补齐。每轮同一问题只扩展一次，
请求 UUID 由扫描 ID 和问题 ID 派生。旧种子、已发送种子仍参与问题发现。文章直接进入候选。
采集器按知乎 `sort_by=default` 的原始顺序和分页游标取得前 20 个不同回答，首请求最多 20 条，保存排名、采集时间
及证据；不足 20 个必须有实际列表结束依据。列表固定后才进行任何过滤，不因过期、已发送或
低分而补第 21 个。原搜索回答即使在前 20 个之外也保留；重合按回答 ID 合并。

扩展回答继承种子的话题和搜索词来源，不要求其正文包含搜索词。每个话题去重前候选上界为
200 + 200 × 20 = 4,200。再次扫描可以读取新的默认排名；问题 ID 不用于内容送达去重。

默认列表含正文时，仅对平台明确标记正常、未裁剪且通过完整性校验的回答复用正文；其余继续读取单篇详情。
全部列表取得后检查历史送达或已登记投递的内容，可以跳过其后续正文请求。其他候选取得完整正文
后按各自发布时间和本轮固定的学习版本评估。时间窗口截至扫描开始时刻；有限窗口拒绝缺失、
不可解析或未来日期。只有日期但无时刻的记录按北京时间当天零点判断；无时区的时间戳不猜测。

扫描完成后按学习分数降序排列，同分时较新内容优先，最多推送 10 篇。尚未有两类有效标签时，
同样最多发 10 篇待校准内容，展示样本进度。并行扫描已经登记的内容不占本轮新内容额度。

## 字面学习

每个稳定内容身份只使用最新有效喜欢或不喜欢修订，训练保留当时的完整正文快照。词表只来自
当前负反馈的降权词，按 casefold 后的正文子串是否出现取 0/1，每词每篇只计一次。

优化目标为两类总权重各 0.5 的平均逻辑损失加 `0.1 / 2 × ||w||²`，约束每个关键词权重不大于
零。训练包含不正则化截距；推送分数始终只取命中关键词权重之和，不含截距。正样本也使用相同
词表，因此可以减轻其中关键词的惩罚。

阈值枚举训练分数的分界，最大化两类平均正确率，平分时优先降低负样本误推数，再选择更高
阈值。阈值不大于零，分数等于阈值通过，未命中降权词的零分内容始终通过。特征相同但标签
相反的样本记入冲突，拟合报告保留逐样本结果和混淆计数。

后台固定反馈修订截止位置再拟合，保存版本、权重、阈值、L2、收敛残差与拟合结果。失败保存
原因并保留之前的有效版本；新反馈会触发新一次训练。同一修订的失败不会在每个后台循环反复
重试。修改反馈后若不足两类样本，即使曾有有效模型也重新进入待校准状态。扫描只用创建时
保存的完整学习快照，途中提交的反馈用于后续扫描。

## 数据、投递与恢复

真实库默认 `data/scout.sqlite3`。首次话题迁移在 sender 锁内通过 SQLite backup API 创建
`scout-before-zhihu-topics-<时间>.sqlite3`，检查 integrity_check 后再添加表和列。主要记录：

| 表 | 内容 |
| --- | --- |
| `zhihu_topics`、`zhihu_settings` | 话题、时间范围、每日计划 |
| `zhihu_scans` | 原配置、开始时刻、学习快照、采集请求和分页任务关联 |
| `zhihu_content_snapshots` | 完整正文和原始内容快照 |
| `zhihu_candidate_discoveries` | 搜索词、种子、问题、默认排名和发现时间 |
| `zhihu_question_expansions` | 每轮问题的固定 UUID、实际回答顺序和覆盖进度 |
| `zhihu_candidate_results` | 过滤原因、得分、学习版本，供误筛补标 |
| `zhihu_feedback_revisions`、`zhihu_learning_versions` | 反馈修订和学习版本，独立于橘鸦 |
| `zhihu_link_deliveries` | 稳定内容身份、固定消息、群、发送 UUID、状态和飞书消息 ID |
| `zhihu_jobs`、`zhihu_card_deliveries` | 后台请求及管理/补标卡片队列 |

回答身份为 `zhihu:answer:<id>`，文章为 `zhihu:article:<id>`。身份不依赖标题、正文、URL 写法、
话题或扫描 ID。旧 `rule_test_deliveries` 中的成功键继续阻止自动推送。发送前持久化身份和完整
消息，待发、发送中、失败都保留同一身份和 UUID；成功后记账。正文补标卡首次发送也登记内容
身份，后续明确请求再次查看可以另发补标卡。

旧任务和旧投递保留文字链接消息；新任务发交互卡片。自动发送最多尝试三次，失败保留原记录；
显式恢复重置次数，沿用 UUID。飞书远端成功和 SQLite 记账不是同一事务，超过飞书 UUID 幂等窗口
的未知结果恢复仍有重复风险。

```bash
# 查看已保存话题、计划、学习信息，不请求模型或飞书
uv run --locked python -m scout.zhihu topics

# 为已配置话题新建一次扫描；0表示只提交，由常驻listener继续
uv run --locked python -m scout.zhihu scan --topic-id 1 --wait-seconds 0

# 复用请求 UUID 不会创建第二个扫描
uv run --locked python -m scout.zhihu scan --topic-id 1 --request-uuid <UUID>

# 查看状态或恢复原扫描的待发消息（包括旧扫描）
uv run --locked python -m scout.zhihu status --run-id <扫描UUID>
uv run --locked python -m scout.zhihu scan --run-id <扫描UUID>

# 恢复失败的管理/补标队列卡，沿用原UUID
uv run --locked python -m scout.zhihu retry-cards
```

正文和原始证据副本、配置及报告位于 `data/zhihu-runs/<UUID>/`。报告分列搜索种子数、扩展问题、
同题候选、历史送达去重、完整正文、各类过滤原因、学习版本与失败状态。扩展失败不会当成
完整零结果。旧 `score --config config.zhihu.toml` 只用于历史格式规则诊断，不更新学习或发送内容；
新扫描报告来自其固定学习版本。`config.zhihu.toml` 不再创建新规则扫描。
