# Scout 权威规格：条目级 LLM 个性化与飞书反馈闭环

本文档描述 Scout 当前行为、数据契约与运行边界。安装和日常操作见 [README](../README.md)。

## 1. 定位和边界

Scout 是单一 owner 的个人工具，个性化是核心能力。正式业务的唯一信源是橘鸦
AI 早报 RSS；只使用橘鸦给出的分类、标题、人工摘要、详情和相关链接信息，不抓原文。
独立的知乎本机采集与单次交付见第 10 节。

每期概览按原顺序拆成条目，LLM 只输出 `推荐 / 不推荐 / 不确定` 与简短中文
理由。`推荐 / 不确定` 按原顺序发送全文，`不推荐` 汇总为当期末尾的标题多选
列表，按需展开正文；不使用数值分数排序。

非目标：多用户或群体偏好、白名单产品功能、其他信源的正式自动推送、embedding、向量
数据库、兴趣分、应用内调度 daemon。listener 与一次性 sender 是独立进程，调度
由 systemd timer 完成。

## 2. CLI 和配置契约

以下模式互斥：

- `--send`：人工更新档案，发送档案变化卡并按日期补齐有效期内未推送日报；
- `--send --scheduled`：白天定时入口，先保存日报，再使用已保存偏好推送；
- `--profile-update`：每日 19:00 更新偏好并通知变化，不发送新闻；
- `--dry-run`：真实采集和模型调用，预览卡片，SQLite 零写入；
- `--calibrate`：忽略整期状态，发送最新一期所有校准卡片，重复只补缺项；
- `--listen-feedback`：阻塞运行飞书长连接并处理 `card.action.trigger`；
- `--profile-show`、`--profile-history`：只读审阅；
- `--profile-rollback VERSION`：复制目标版本为新的活动版本；
- `--profile-rebuild-preview`：真实模型全量重整预览，显示结果和输入规模，SQLite 零写入，不发送消息；
- `--profile-rebuild`：强制全量重整、激活新版本并通知飞书群，不运行新闻推送。

`--issue-date YYYY-MM-DD` 只可用于 `--send/--dry-run`，精确选择一期并绕过年龄
限制及整期基线，条目去重继续生效。优先 RSS；过期或 RSS 不可达时只接受已有完整
快照，缺失时明确报错。日期选择失败发生在模型归纳与档案通知之前。普通发送合并
RSS 与本地完整快照，按日期从早到晚补齐有效期内未推送日报，沿用现有年龄边界和
去重规则。有效期外的历史补发逐期指定。`--scheduled` 禁止与 `--issue-date` 同用。

`--send/--dry-run`、`--profile-update` 与两个重整命令必须有合法 `models.toml` 和
`SCOUT_LLM_API_KEY`。两个重整命令均不接受 `--issue-date`。校准、
listener、档案审阅与回滚不调用模型。listener、发送和校准要求飞书 App ID/Secret
及接收者类型与 ID；正式重整也要求这些飞书配置，正式重整及个性化发送必须使用
`chat_id` 群目标。按需正文以原列表保存
的群 ID 为目标，之后配置变更不会改变旧列表的正文去向。

`config.toml` 使用单个 `[source]`，保留 name/url/window_size/max_age_days，固定 RSS，无 collector 字段。
`models.toml` 使用 `[model]`，仅有 model/base_url。协议固定为 OpenAI Responses，密钥变量固定为
`SCOUT_LLM_API_KEY`，端点 URL 不得携带凭据、query 或 fragment。配置校验集中在加载入口。

Responses 请求固定 600 秒超时、关闭 SDK 重试、`store=false`。偏好归纳和条目
评价统一设置 `reasoning.effort=max` 和 `max_output_tokens=65536`，预算包含思考
与最终答案。输出使用严格
`text.format` JSON Schema；客户端检查 `status == completed`，通过
`output_text` 读取 JSON，并在失败时处理 `incomplete_details`。不降级到自由文本。

## 3. 核心类型和条目规范化

`DigestArticle` 包含日报键、概览位置、编号、分类、标题、原文 URL、橘鸦摘要、
详情、相关链接、稳定条目键和内容哈希。

`PersonalizedEvaluation` 包含条目键、三态结论和中文理由。

`PreferenceProfile` 包含档案版本、格式版本、带标识的结构化条目、逐条反馈依据、
版本变化摘要、通知状态和已处理反馈修订位置。格式 v2 的分类为判断规则（rules）、
具体对象（entities）、专题兴趣（interests）、重要疑问（questions）。格式 v1
的喜欢规则、不喜欢规则、权衡项和不确定项仍可展示、回滚。评价输入与飞书卡只使用
可读内容；证据与历史版本保存在 SQLite。

条目键优先使用去除 fragment 与跟踪参数后的规范化原文 URL。无 URL 时使用
`日报键 + 编号`；再无编号时使用 `日报键 + 位置 + 标题哈希`。内容哈希覆盖分类、
标题、规范化 URL、摘要、详情和相关链接。

概览与正文按以下顺序一对一匹配：规范化 URL、编号、唯一规范化标题、相同位置。
任何正文匹配失败都保留概览条目，只把摘要、详情和相关链接留空。

## 4. SQLite 数据与事务

`source_state`、`baseline_items`、`delivered_items` 分别记录来源初始化、首轮基线
和整期完成状态。历史库中的 `active_failures` 表及数据保留，当前运行不再使用。
其余业务表如下：

- `article_snapshots`：以日报、条目键和内容哈希保存不可变输入快照；
- `card_deliveries`：关联快照、用途、三态评价、`message_id/chat_id`；
- `scout_owner`：只允许 singleton=1，第一次有效反馈原子绑定 `open_id`；
- `feedback_revisions`：每次有效修改追加不可变修订；
- `preference_profiles`：版本、父版本、格式化内容、证据汇总、活动状态、通知状态和回滚来源；
- `preference_entries`：按档案版本保存带唯一标识、分类和位置的条目；
- `preference_entry_evidence`：逐条引用不可变反馈修订，外键关联条目及原始反馈；
- `preference_updates`：每个新版本的更新方式、触发原因、输入反馈条数、真实新增修订
  条数、本轮开始时距上次全量的修订数、上次成功全量截止位置和模型输入字符数；
- `evaluation_cache`：按条目键、内容哈希与档案版本缓存严格评价。
- `issue_snapshots`：按源及日报日期保存完整日报输入与规范化条目清单；旧版原子
  保存的橘鸦条目快照仅在位置连续且摘要、详情齐备时用于历史回退；
- `filtered_lists`：日报、分页编号、发送 UUID、消息关联及列表刷新版本；
- `filtered_list_members`：不可变条目快照、位置、当时判断理由和档案版本，条目键唯一；
- `reveal_submissions`：记录真实回调事件 ID，防止同事件重放重置失败批次；
- `reveal_requests`：每成员唯一的正文发送 UUID、请求批次、状态、尝试次数和送达关联。

写入使用短事务、外键和 5 秒 busy timeout。sender 另使用非阻塞文件锁，
防止 timer 与人工发送重叠。每日偏好更新、正式偏好重整和回滚共用此锁，覆盖读取、模型调用、
提交及通知；模型调用期间不持有 SQLite 写事务。listener 用独立文件锁防止同时
启动两个后台发送线程。
正文请求回调只等待 SQLite 写锁最多 500 毫秒；失败可安全重新提交。

整期送达与条目卡片送达分开。校准忽略旧的整期状态，并按“快照 + calibration”
判断缺项；普通发送把任意历史卡片或已成功呈现列表中的同条目键视为已处理。只有
本期所有条目均已送达正文或已在列表呈现，才写 `delivered_items`。正文请求仅按
正文送达记录去重。尚未成功发送的列表不算呈现，但保留列表计划，重试仍使用原
快照、评价、分页及 UUID。远端成功后立即保存卡片 ID。

## 5. 偏好增量归纳与定期重整

### 内容与提示词

- 判断规则：喜欢或不喜欢的共性条件，例外尽量写入对应规则。
- 具体对象：明确关注或不关注的产品、公司及其与 owner 的关系，避免在规则中反复列举。
- 专题兴趣：通用规则无法充分表达的明确兴趣，例如模型破甲。
- 重要疑问：确实影响推荐、现有反馈无法解决的歧义；可以为空。

输出完整的新偏好，允许合并、改写、删除；上一版不要求逐条保留。重复反馈用于
印证已有判断，不自动新增规则。不复述新闻案例，不从单条新闻评价推断整个领域
的喜恶。保留明确表达的对象、关系和兴趣，不为精简丢失区分度。不为每个兴趣推演
未知边界，删除已解决或不影响判断的疑问。判断规则争取不超过 10 条、重要疑问
争取不超过 3 条，均为软目标，不在程序中机械截断。每条结论必须关联有效依据，
但不要求每条反馈都形成规则。

### 触发与输入

首次生成沿用当前有效反馈至少 2 条喜欢、2 条不喜欢的启动条件。普通更新只输入
当前精简偏好及上次成功更新后新增的有效反馈，保留倾向、原因和原新闻标题、摘要、
详情的完整上下文，不另设信息筛选模型。输出完整偏好及新增、合并、修正、删除或
保持不变的变化说明；即使规则不变，也保存新版本、处理进度和更新记录。

以下情况直接全量重整：首次生成、旧格式切换、距上次全量累计达到 20 条真实反馈
修订、修改已处理反馈、手动重整、回滚后首次出现新反馈。达到阈值或发现修改时
直接请求全量，不先请求增量。判断是否修改已处理反馈以同一 delivery 在已处理
截止位置前是否有反馈为准，即使旧反馈未形成具体规则，也要重整。

全量输入每张新闻卡片当前有效的最新版反馈及原新闻上下文；仅依据反馈重新归纳，
旧偏好仅用于变化说明。不恢复已替换修订中的旧判断。首期不做历史分批归纳，完整
请求超出模型容量时明确失败，不静默截断或丢弃历史。模型继续使用 65536 token
输出预算与 600 秒超时。

### 读取快照、证据和原子提交

每轮偏好更新在同一个 SQLite 只读事务内获取活动版本、反馈最大修订位置、有效
反馈、真实修订计数和修改标志。模型调用前关闭读取事务；之后到达的修订留待下一
轮，包括调用期间对已有反馈的修改。消费截止位置不会前移到模型结束时的最新值。

模型输出顶层仅有 format_version（整数 2）、entries 和 change_summary。
entries 中每条具有全局唯一 id、四选一 category、可读 text 和非空 evidence_refs；
证据引用只能归属具体条目，不能在顶层添加证据字段。
全量只能引用本轮 `f:修订ID`；增量还可引用 `p:上版条目ID`，程序将它展开为
SQLite 内的原始反馈依据，避免把历史证据 ID 集合输入模型。程序检查输出格式、
条目唯一性、引用范围及展开后的证据；不存在、空依据或在固定截止位置已被替换
的引用都会失败。全量不允许引用旧条目，不要求覆盖全部反馈。

提交时再次验证活动父版本、截止位置与有效依据；新偏好、逐条证据、活动版本和
更新/消费进度一次事务提交。保留旧格式 JSON 和所有旧版本及不可变反馈。
`last_full_feedback_revision_id` 保存最近成功全量重整的截止位置；阈值使用
`COUNT` 计算其后真实修订数，不能用 ID 差值代替。更新记录中的
`revisions_since_rebuild` 是本轮开始时距前次全量的计数，成功重整后下一轮从新
截止位置重新计数。

日志与 show/history 提供 mode、trigger、feedback_count、revision_count、
rule_count、entry_count、readable_chars 和 input_chars。input_chars 统计
instructions + JSON 输入 + 输出 schema 的字符总数，不标称为 token 数。
评价模型输入和飞书偏好卡不包含完整历史证据 ID，只展示可读偏好。

### 失败、通知、预览和回滚

新版本先原子激活，再发送偏好变化卡。通知失败保留待通知状态，本轮停止，不能
继续新闻发送。重试先补发活动版本；正式重整重试时若没有新反馈，通知成功即结束，
不再次调用模型。已有新反馈时先通知待发版本，再按固定快照更新。模型失败或校验
失败不推进消费进度，不用旧档案继续本轮人工新闻发送。19:00 自动更新失败则保留
原档案供次日白天使用，并在下一次 19:00 重试；白天不会补发偏好通知或消费新反馈。

`--profile-rebuild-preview` 总是执行真实全量请求（仍受首次 2+2 条件约束），输出
完整临时偏好和输入规模，不初始化 SQLite、不写库、不创建写操作锁、不联系飞书。
`--dry-run` 对待处理反馈生成临时偏好用于评价，不写版本、消费进度或评价缓存。
正式 `--profile-rebuild` 只重整并通知，不采集或推送新闻。

回滚复制目标版本内容及历史依据，生成更大版本并标记待通知，在同一事务将当前
反馈标为已处理。没有新反馈时不能因为旧格式迁移立刻反弹；首次新反馈触发全量
重整。手动重整可随时覆盖回滚版本。回调仍不调用模型，在下一次偏好更新开始时
直接处理已到达的修改；listener 不因反馈自动启动 sender。

## 6. 条目评价和发送

评价输入携带当前档案，以及本轮固定读取快照内最近各 4 条喜欢与不喜欢的有效反馈；
不会混入偏好归纳期间新到达的反馈。条目按概览
顺序每批最多 8 条。结构化输出的条目 ID 必须完整对应请求且无重复，否则整批
失败。模型返回顺序可不同，程序按请求顺序归位。

某批评价失败后，后续批次继续评价并缓存；正文在最早缺项处暂停以保持原顺序。
整期不标记完成，下次只补缺项。本期评价和推荐/不确定正文均完成后才创建并发送
末尾不推荐列表；中途失败不发不完整列表。多页列表的计划一次提交，发送失败后
按原分页补齐。
每张卡片展示标题和原文链接、分类与编号、橘鸦摘要/详情、三态判断和个性化理由，
不展开完整相关链接列表。不推荐正文仅在 owner 从列表请求后发送。

末尾列表标题包含日报日期及当前卡片条目数；每行只有完整新闻标题和勾选框，底部
有“推送所选正文”。使用 JSON 1.0 `form` 内的 `checker`，不在勾选时触发回调，
通过按钮一次提交表单。按卡片字节容量和每张最多 50 个成员拆分编号卡片，为状态
文案和数据库 ID 留出容量。不截断标题；单标题仍超限时明确失败，不丢条目。
没有不推荐条目时不发列表；全是不推荐时只发列表（独立的档案变化通知仍可发送）。

列表呈现与展开正文不构成喜欢，不写反馈。正在发送、重试中及已送达正文的勾选框
禁用；未选项可追加。三次失败后恢复勾选并在列表说明可重新选择重试。旧列表和
其判断理由不随偏好版本变化而更新。

## 7. 飞书反馈状态机

1. 新闻卡片提供“喜欢”和“不喜欢”；
2. 点击后保留原卡片头部、正文和 Scout 判断，只把底部操作区替换为已选倾向的
   表单，尚不写库；
3. 原因输入必填，服务端再次验证去空白后为 1–500 字；
4. 提交时验证快照、用途与回调 `open_message_id`，在一个事务里绑定 owner 并追加
   反馈修订；
5. 回调保留原卡片正文，并把底部表单替换为“已记录”、原因、修订 ID 和“修改
   反馈”；“修改反馈”可回到选择状态；
6. 与当前最新反馈完全相同的重试不插入新修订，真正修改才追加。

回调路径不调用 LLM。档案自动更新在每日 19:00 执行；人工 `--send` 仍可主动更新。白天定时发送不更新档案。listener 使用
官方长连接事件分发；项目内兼容 `lark-oapi 1.7.2` 未分发 CARD 帧的问题。旧卡片
所需上下文全部来自 SQLite，因此 listener 重启后仍可提交。

`reveal_selected` 回调验证已有的唯一 owner、原列表消息及群 ID、所有表单成员
和布尔勾选值，以一个短事务记录事件及请求，立即回复提示。该操作不能绑定新
owner，不调用模型或在回调内逐条发送。后台线程收到唤醒后立即处理 SQLite 队列，
同次提交按原概览顺序发送至原群；失败最多尝试三次，保留同一 UUID。重复提交
只加入尚未发送或已耗尽重试的成员，同一事件重放不重启失败批次。

后台发送成功后，在同一事务写入现有 `card_deliveries`、完成请求并标记列表需
刷新。正文使用原列表保存的评价，并复用全部旧反馈交互。后台线程单独刷新原列表，
回调只返回提示，避免同步回调卡片覆盖较新的后台状态。刷新失败不重发正文；
列表版本防止遗漏并发追加选择，三次刷新失败后可通过再次提交或重启重试。
重启恢复中断请求，累计尝试次数；已经耗尽三次的正文请求等待 owner 重新选择。

## 8. 自动运行

`scout-feedback.service` 常驻 listener，`Restart=on-failure`。
`scout-send.service` 执行 `--send --scheduled`，每天北京时间
09:30、10:00、10:30、11:00、11:30、12:00、12:30 检查日报。
`scout-profile-update.service` 执行 `--profile-update`，每天 19:00 更新偏好。
两个 timer 均显式使用 `Asia/Shanghai`、`Persistent=false` 和 1 秒触发精度，
晚间不抓取 RSS，重启不补触发。白天任务在入口检查 09:30–12:30 窗口，
12:30 这一分钟启动的任务可以正常运行至完成。

定时发送先读取本地完整日报；当天完整快照存在则不请求 RSS。否则抓取并在模型
调用前解析、保存有效期内日报。只有成功提交的完整快照才表示抓取成功；已有
快照跨进程重启复用。RSS 失败仍处理本地待发送内容。日期升序补齐，较早一期
未完成时暂停后续日期；保留评价缓存、正文和列表送达记录，仅重试未完成部分。
全部完成后跳过偏好、模型和飞书阶段。`max_age_days=3` 只排除发布时间的北京
日期早于“今天减 3 天”的日报，边界当天仍有效。12:30 后发布的日报次日补抓。

19:00 任务在一致的只读事务中固定不晚于当天 19:00 的已保存反馈，再调用现有
自动增量／全量更新逻辑；之后提交的反馈留到次日。没有变化和待通知版本时直接
退出。模型或保存失败保留原偏好及消费进度，次日 19:00 重试；通知失败保留已激活
的新版本和待通知状态。白天仅使用最近一次已保存偏好和其已消费反馈，没有可用
偏好时保存新闻快照并停止发送。人工发送及重整入口保留主动更新能力。

## 9. 工程检查与验证边界

项目不编写单元测试。不需要飞书端到端验收的变更不写测试；本地静态检查命令见
[README](../README.md#工程检查与已知边界)。需要验收时，只使用真实橘鸦 RSS、
当前模型端点、真实 SQLite 和真实飞书群，核对卡片内容与顺序、真实反馈落库、
偏好及消费进度、重复运行去重和服务重启恢复。不伪造反馈或回调，不为覆盖分支
重放已完成日报。

涉及以下行为的变更，应使用对应真实场景验收；未实际触发的分支不得宣称已通过：

- 自动调度完整链路、晚发布补抓、跨日重启和模型／发送失败恢复；
- 列表重复及追加选择、重试耗尽后重新选择、中断请求恢复、长列表分页、没有不推荐
  或全是不推荐的日报；
- 偏好重复／新增兴趣处理、已处理反馈修改、20 条修订阈值、模型调用期间到达的
  反馈、回滚后新反馈和通知失败补发。

列表及按需正文使用持久化 UUID 和唯一约束；飞书同 UUID 仅保证 1 小时内发送去重。
飞书成功与 SQLite 提交不能跨系统原子化，超出此窗口的未知结果重试仍可能重复。
普通正文及档案变化通知在远端成功后本地记账，该间隙中断也可能导致重试重复。

组件与接口依据：[checker](https://open.feishu.cn/document/feishu-cards/card-components/interactive-components/checker)、
[form](https://open.feishu.cn/document/feishu-cards/card-components/containers/form-container)、
[发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)、
[更新卡片](https://open.feishu.cn/document/server-docs/im-v1/message-card/patch)。

## 10. 独立知乎本机采集与单次交付

知乎采集器独立部署于 `/home/dev/workspace/mediacrawler-scout`，使用固定上游提交
及独立适配分支、依赖锁、浏览器会话、任务 SQLite 和证据目录。Scout 经本机
HTTP/JSON 协调，保存访问令牌，不导入采集器模块或读取采集器内部数据库。
接口和部署步骤见[知乎本机采集说明](zhihu-validation.md)。

`python -m scout.zhihu` 仅提供 `status/scan/score`。新扫描保存自动通知标记、规则和目标群。
查询、排序、页数、批量、正文规则均由配置决定；每个查询最多三页，max_unique 在 1–200，
max_results 默认 5，允许不超过 max_unique 的正整数。当前主题只是默认配置。
搜索后按 ID 请求详情，校验完整性与证据哈希。失败、摘要和部分正文不能用于通知。

每批正文保存后按发现顺序登记合格新文章。历史已送达和其他扫描已登记文章不占结果额度。
每篇发送一条“标题＋换行＋原文 URL”文本消息。`score` 只生成报告，不改变通知队列。
不再支持正文卡片、人工语境核对文件、preview/send-test/send-results 或旧模块转发。

`zhihu_link_deliveries` 固定文章键、扫描归属、标题、URL、群、UUID、状态、尝试次数、
重试时间和消息 ID。先落库再发消息，网络期间不持有 SQLite 事务。CLI 与 listener 共用
恢复流程及进程锁，扫描终态仍推进通知。每条自动尝试最多三次，间隔至少 5 秒、15 秒；
耗尽暂停该扫描的后续链接。`scan --run-id` 重置失败项的尝试次数，保留 UUID 与内容。
成功送达记录全局去重，旧 `rule_test_deliveries` 的 delivered 记录同样参与去重。
历史扫描没有 auto_notify 标记，不因升级补发；旧待发卡片不会被新队列接管。

首次启用新表必须在 sender 锁内通过 SQLite backup API 备份现有数据库，并确认备份
integrity_check 为 ok 后建表。所有历史表、偏好版本、日报快照和采集证据保留。
初始化在写入口或后台任务启动时进行，普通读取不执行建表或迁移。

登录由独立采集器的 Cookie 导入和实际账户验证完成。无有效会话时扫描等待，验证通过
继续原任务。listener 后台线程每 5 秒推进；采集采用单次任务，没有周期采集 timer。
平台额外验证不能绕过，登录恢复见 [Cookie 导入说明](zhihu-cookie-import.md)。
操作、退出码及证据文件见 [知乎采集说明](zhihu-validation.md)。

历史日报快照的两处 NewsItem 反序列化入口仅忽略 `first_seen_at`、`updated_at`、
`summary_html` 三个已知扩展字段。其余未知字段仍报错，不改写原始快照或数据库表。
